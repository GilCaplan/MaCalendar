MACalendar · internals

Reading the
assistant's mind

A voice-driven calendar that runs entirely on one laptop — you speak, and an event or a task appears. This page opens it up: how it decides what you meant, when it trusts a set of rules over a language model, and how it learns the words you use that no dictionary contains.

00What it is, in one paragraph

Speech is transcribed on the machine's own GPU. A keyword-and-grammar parser tries to understand the sentence; if it is unsure, a language model running locally reads it instead. Whatever they decide is checked against a list of deterministic sanity rules, written to a SQLite file, and then read back by the model as a second opinion. Nothing is sent anywhere: no account, no API key, no server. The interesting parts are the seams — where one component hands to another, and what happens when it hands over something wrong.

It is also aware of the Jewish calendar. Sundown is computed from the configured latitude and longitude, so the system knows when Shabbat and festivals begin and end — not as dates, but as moments that shift through the year. Repeating events skip them; a training planner will not schedule a run on one. Section 06 covers how that works.

00bThree models, and what each one is for

Worth settling early, because the rest of the page keeps referring to them. There are three, they are all small, and they all run on the one machine.

Two absences are as informative as the three presences. There is no embedding model: finding your similar past commands is done with word-overlap arithmetic, not vectors, because a fourth model would have to stay resident to search a few hundred short strings. And there is no classifier model: the labels that colour an event or tag a task come from keyword scoring and a personal word list. Both are choices that section 07 lists as unmeasured.

That last box is the part most descriptions of this pattern get wrong, so it is worth stating plainly: the model reviews every command, including the ones the rules were completely confident about. A confident wrong answer is precisely the case nothing else would catch.

Six jobs, one model

The 8B model is loaded once and stays loaded. It is asked six different questions, with six different prompts, and only three of them happen while you are waiting:

Why so small? The whole assistant has to sit resident on a laptop that is also being used for other things. The 8B model is pinned in memory permanently so the first command of the day is not slow — which is only a reasonable thing to do because it is 8B. Every design choice on this page is downstream of that: the rules exist so the model is not needed for the easy two-thirds, and the review runs in the background so its cost is invisible.

01One number decides everything

Every command is scored for confidence before anything happens to it. Above 0.85 the rules answer it themselves, in about a tenth of a second; below it, the sentence goes to llama first. That threshold routes roughly 44% of commands one way and 56% the other.

It decides who answers first, not who gets the last word. The event is written either way, and then llama reads every command back — including all of the 44% it never saw. The threshold buys speed, not autonomy. 

# how the number is built — rule_parser.py:_compute_confidence
base       = required slots filled ÷ required slots   # "did I get everything?"
           × 0.95   if the date came from regex, not the recogniser
           × 0.85   if the domain was guessed from the open view
           × 0.80   if it resolved "it" / "that one" to a past event
           × 0.70   if two clock times appeared — probably two events
           + 0.05   per optional slot filled, capped at +0.10

01bIs that formula any good?

The shape is standard. AWS Lex routes to an LLM when NLU confidence falls below a configured threshold; Voiceflow pairs a fine-tuned classifier with Claude the same way, reporting that a threshold of 0.7 lets the small model cover about 80% of requests at roughly 85% accuracy. Confidence-then-fallback is the ordinary design.

The difference is where the number comes from. Those systems read a probability off a trained model and then calibrate it — Platt scaling, temperature scaling — so that "0.85" actually means "right about 85% of the time". This formula's multipliers were chosen by hand: 0.95, 0.85, 0.80, 0.70, and a threshold that happens to equal one of them. None has been checked against outcomes.

Calibration is measurable here and has never been measured. The audit records both the confidence and whether the command was right, so bucketing by score would show it directly: if commands scoring 0.85–0.90 are right 88% of the time, the number means something. If they are right 97% of the time, the threshold is too cautious and work is being sent to the model for nothing. Either answer is more useful than the formula's current status, which is "plausible, and untested".

02How the rules read a sentence

No model. spaCy tags the words, a date recogniser lifts times out, and a table of 76 verb → action mappings decides what you asked for. Nine of the fifteen actions are reachable this way; the rest always need llama.

The verb lookup tries four things in order, and the fourth is where it goes wrong: 

1. the ROOT verb, if it maps to an action        ← "book a haircut tomorrow"
2. the ROOT verb even if it doesn't, for WH-questions
3. any VERB or AUX in the span that maps
4. any token at all — any part of speech —
   whose lemma maps to an action                 ← the trapdoor

How it is caught now. Not by lowering the confidence — that rule is load-bearing. The action runs, matches no such task, and raises TargetNotFound; the command is then re-read by llama, which returns create_event. Being wrong is detected by trying, not by doubting.

04How it learns you

The part people mean when they ask whether it is "trained on me". It is not fine-tuned — nothing about llama changes. Instead, your four most similar past commands are pasted into the prompt as worked examples, under a header telling the model to match your phrasing and habits. 

USER HISTORY — how this user's past commands were (correctly) interpreted.
- "Set a meeting for 10 a.m. tomorrow morning" (user-corrected)
    → {"action": "create_event", "title": "Team Standup", "start_time": "10:00"}
- "set meaning for tomorrow at 7 p.m. with the team"
    → {"action": "create_event", "title": "meaning", "start_time": "19:00"}

Two flaws worth knowing. The header claims these were "correctly interpreted", but 48% of the pool has never been reviewed — success=1 only means nothing threw. And the candidate pool is the most recent 2,000 commands, so a correction you made deliberately becomes unreachable after about ten months of ordinary use. The cheapest signal evicts the dearest.

05How it becomes yours

Nothing about llama changes — no fine-tuning, no weights. What personalises the assistant is four small stores it consults, all of them plain files you can open, edit and delete. This is the part that turns a generic parser into one that knows that a word your dictation keeps mangling is the name of a course you take, and that another is your dog.

What a personal word can carry

An alias corrects something you did not say, so replacing it loses nothing. An acronym is what you said — expanding it in your task would be editing your words, not correcting them. That distinction is why they are different fields rather than one.

Why the labels matter beyond colour

For events a label is mostly a colour: the category picks one, and an alternate shade so two adjacent events are never identical. For tasks it does more work — the label is how you find things, filter them, and see at a glance that half your list is shopping. That is why half of untagged tasks was a real problem and a third of uncoloured events was mostly cosmetic.

What is missing. These three stores still learn separately. The vocabulary knew the course's name for months while the tagger had no idea it meant coursework — that link was only added recently, and nothing yet connects task tags to event categories, so "Running" and "Gym" exist as event labels with no home in the registry and no relationship to "Exercise". A two-level hierarchy is the intended fix and is not built.

06What it actually knows about time

Sundown is computed from your latitude and longitude with astral, and the Hebrew date from pyluach — both pure Python, no lookup. That makes Shabbat a moving boundary rather than a day of the week. 

Fri  4 Sep   candles 18:43   →  19:00 falls inside Shabbat
Fri 18 Dec   candles 16:20   →  17:00 falls inside, 16:00 does not
Sat  5 Sep   tzeit   19:37   →  20:00 is out

A repeating event skips those windows, with three exceptions that are all about intent: meals are allowed because they are what the day is for (unless it is a fast — Yom Kippur is both, and the fast wins); a series anchored on Shabbat keeps it, because a Saturday shiur was put there deliberately; and if observance cannot be computed, nothing is skipped, because a series quietly losing days is worse than one landing where it should not.

06bMore than one thing at once

A single sentence can hold two events, and the rule parser cannot: it has one set of slots. Rather than fill half of them it refuses outright — RuleParserSkip — and the sentence goes to llama whole. A softer version of the same instinct is in the score: two clock times in one span multiplies confidence by 0.70, because "lunch at noon and coffee at 9" is usually two things wearing one sentence.

Batching works the other way. Several commands can be sent as one request with each in brackets — [gym tomorrow at 7am] [lunch with Dana at noon] — and the server splits them and parses each alone. That is cheaper rather than dearer, because a short single command often settles on the rules for no model call at all, and the review runs once for the batch instead of once each.

Two commands sent asLLM calls
two separate requests4
[one] [two] — split and parsed apart3
"one and two" — one run-on sentence2

Joining is cheapest and worst: it buys one call by handing the model the run-on sentence it is least reliable on. Brackets are the middle, and the saving is the review, not the parse.

06cWaiting, and coming back to it

Two different queues, easy to confuse because both are "later".

QueueWhat it holdsDrains when
the session queue pressing the mic while it is still thinking — the next thing you want to say, or (press again) more of the same sentence the current command finishes
the pending queue a command the model could not be reached for — Ollama down, laptop asleep. Stored with its transcript, never silently dropped a retry loop notices the model is back

Neither blocks you. The phone shows a queued command as pending and gets a notification when it finally ran, which is the only reason a command given on a train is still there when the laptop wakes up.

06dTasks are not small events

Eight of the fifteen actions are about tasks, and they behave differently from events in ways worth knowing: a task has no time, it has a list, and it can be finished.

PropertyBehaviour
list"today" or "general" — where it lives, and what a daily read covers
tagsinferred from the title, or from your own vocabulary
due dateoptional, and the only date a task has
subtasksa task can hold its own list; each completes separately
completionfinished, not deleted — the record survives

The distinction the parser has to make first is event or task, and it hinges on whether a time was spoken. "Remind me to buy milk" is a task; "buy milk at 6" is an event. That single judgement is why the self-check's routing rules spend most of their words on it.

06eReading the day back

Asking is a first-class action, not a search box. query_schedule and query_todos answer in sentences, and because they create nothing they are the one place the self-check may not act — there is no record to correct. 

"what do I have on friday"
  → You have one event Friday, 4 September: Dentist Appointment at 9:00 AM.

"what do I have this week"
  → You have 6 events this week: Team Standup at 9:30 AM, ...

A named day beats the relative scope: scope can only say today, tomorrow or this week, so "friday" used to fall through to today and answer confidently about the wrong day. It now carries an explicit date, and the answer names the day back to you — "Friday, 4 September" — so a misunderstanding is visible in the reply rather than discovered later.

The morning briefing is the same query with no question: it reads today's events aloud in order, in one sentence, and says "your schedule is clear" rather than nothing at all when there is nothing.
