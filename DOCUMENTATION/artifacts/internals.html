MACalendar · internals

Reading the
assistant's mind

A voice-driven calendar that runs entirely on one laptop — you speak, and an event or a task appears. This page opens it up: how it decides what you meant, when it trusts a set of rules over a language model, and how it learns the words you use that no dictionary contains.

What it isone paragraph you can stop after

01What it is, in one paragraph

Speech is transcribed on the machine's own GPU. A keyword-and-grammar parser tries to understand the sentence; if it is unsure, a language model running locally reads it instead. Whatever they decide is checked against a list of deterministic sanity rules, written to a SQLite file, and then read back by the model as a second opinion. Nothing is sent anywhere: no account, no API key, no server. The interesting parts are the seams — where one component hands to another, and what happens when it hands over something wrong.

It is also aware of the Jewish calendar. Sundown is computed from the configured latitude and longitude, so the system knows when Shabbat and festivals begin and end — not as dates, but as moments that shift through the year. Repeating events skip them; a training planner will not schedule a run on one. Section 09 covers how that works.

01bHow much of it there is

"A voice-driven calendar" undersells it, and the undersell matters, because most of the decisions later on only make sense at the real scale. What is actually here:

DomainWhat it holdsReachable by voice?
calendarevents, repeating series, colour categories, guestsyes
taskslists, tags, sub-tasks, quantities, due datesyes
trainingexercises, templates, plans, logged sessionspartly
courseworkcourses and assignments, linked to calendar entriesno — screen only
time trackingtimers, sessions, tally counters, earningsno — screen only

Fifteen actions, a hundred endpoints, roughly 34,000 lines. The voice layer that the rest of this page describes reaches two and a half of those five domains — and that is a drawn line, not an unfinished one. Speech is good at "book the dentist Thursday at four" and bad at "start the timer on the third project and log the last forty minutes to it retroactively". Where a screen is the better instrument, there is only a screen.

The consequence worth carrying forward: the parser is one entry point into the data, not the owner of it. Every domain above is also edited directly, on two devices, sometimes while disconnected. That is why the last few sections are about rows, versions and conflicts rather than about language — a good deal of the hard engineering here sits downstream of the sentence, not inside it.

02Three models, and what each one is for

Worth settling early, because the rest of the page keeps referring to them. There are three, they are all small, and they all run on the one machine.

Whisper base74 Mthe laptop's GPUsound → words
spaCy en_core_web_sm13 MBCPU, in-processwhich word is the verb
Llama 3.1 8B8 B, 4-bita local server on :11434meaning — and the judging of meaning

Two absences are as informative as the three presences. There is no embedding model: finding your similar past commands is done with word-overlap arithmetic, not vectors, because a fourth model would have to stay resident to search a few hundred short strings. And there is no classifier model: the labels that colour an event or tag a task come from keyword scoring and a personal word list. Both are choices that section 07 lists as unmeasured.

That last box is the part most descriptions of this pattern get wrong, so it is worth stating plainly: the model reviews every command, including the ones the rules were completely confident about. A confident wrong answer is precisely the case nothing else would catch.

Six jobs, one model

The 8B model is loaded once and stays loaded. It is asked six different questions, with six different prompts, and only three of them happen while you are waiting:

Why so small? The whole assistant has to sit resident on a laptop that is also being used for other things. The 8B model is pinned in memory permanently so the first command of the day is not slow — which is only a reasonable thing to do because it is 8B. Every design choice on this page is downstream of that: the rules exist so the model is not needed for the easy two-thirds, and the review runs in the background so its cost is invisible.

How it decidesone section per decision, in the order it makes them

03One number decides everything

Every command is scored for confidence before anything happens to it. Above 0.85 the rules answer it themselves, in about a tenth of a second; below it, the sentence goes to llama first. That threshold routes roughly 44% of commands one way and 56% the other.

It decides who answers first, not who gets the last word. The event is written either way, and then llama reads every command back — including all of the 44% it never saw. The threshold buys speed, not autonomy. 

# how the number is built — rule_parser.py:_compute_confidence
base       = required slots filled ÷ required slots   # "did I get everything?"
           × 0.95   if the date came from regex, not the recogniser
           × 0.85   if the domain was guessed from the open view
           × 0.80   if it resolved "it" / "that one" to a past event
           × 0.70   if two clock times appeared — probably two events
           + 0.05   per optional slot filled, capped at +0.10

04Is that formula any good?

The shape is standard. AWS Lex routes to an LLM when NLU confidence falls below a configured threshold; Voiceflow pairs a fine-tuned classifier with Claude the same way, reporting that a threshold of 0.7 lets the small model cover about 80% of requests at roughly 85% accuracy. Confidence-then-fallback is the ordinary design.

The difference is where the number comes from. Those systems read a probability off a trained model and then calibrate it — Platt scaling, temperature scaling — so that "0.85" actually means "right about 85% of the time". This formula's multipliers were chosen by hand: 0.95, 0.85, 0.80, 0.70, and a threshold that happens to equal one of them. None has been checked against outcomes.

Calibration is measurable here and has never been measured. The audit records both the confidence and whether the command was right, so bucketing by score would show it directly: if commands scoring 0.85–0.90 are right 88% of the time, the number means something. If they are right 97% of the time, the threshold is too cautious and work is being sent to the model for nothing. Either answer is more useful than the formula's current status, which is "plausible, and untested".

05How the rules read a sentence

No model. spaCy tags the words, a date recogniser lifts times out, and a table of 76 verb → action mappings decides what you asked for. Nine of the fifteen actions are reachable this way; the rest always need llama.

The verb lookup tries four things in order, and the fourth is where it goes wrong: 

1. the ROOT verb, if it maps to an action        ← "book a haircut tomorrow"
2. the ROOT verb even if it doesn't, for WH-questions
3. any VERB or AUX in the span that maps
4. any token at all — any part of speech —
   whose lemma maps to an action                 ← the trapdoor

How it is caught now. Not by lowering the confidence — that rule is load-bearing. The action runs, matches no such task, and raises TargetNotFound; the command is then re-read by llama, which returns create_event. Being wrong is detected by trying, not by doubting.

07How it learns you

The part people mean when they ask whether it is "trained on me". It is not fine-tuned — nothing about llama changes. Instead, your four most similar past commands are pasted into the prompt as worked examples, under a header telling the model to match your phrasing and habits. 

USER HISTORY — how this user's past commands were (correctly) interpreted.
- "Set a meeting for 10 a.m. tomorrow morning" (user-corrected)
    → {"action": "create_event", "title": "Team Standup", "start_time": "10:00"}
- "set meaning for tomorrow at 7 p.m. with the team"
    → {"action": "create_event", "title": "meaning", "start_time": "19:00"}

Two flaws worth knowing. The header claims these were "correctly interpreted", but 48% of the pool has never been reviewed — success=1 only means nothing threw. And the candidate pool is the most recent 2,000 commands, so a correction you made deliberately becomes unreachable after about ten months of ordinary use. The cheapest signal evicts the dearest.

08How it becomes yours

Nothing about llama changes — no fine-tuning, no weights. What personalises the assistant is four small stores it consults, all of them plain files you can open, edit and delete. This is the part that turns a generic parser into one that knows that a word your dictation keeps mangling is the name of a course you take, and that another is your dog.

What a personal word can carry

An alias corrects something you did not say, so replacing it loses nothing. An acronym is what you said — expanding it in your task would be editing your words, not correcting them. That distinction is why they are different fields rather than one.

Why the labels matter beyond colour

For events a label is mostly a colour: the category picks one, and an alternate shade so two adjacent events are never identical. For tasks it does more work — the label is how you find things, filter them, and see at a glance that half your list is shopping. That is why half of untagged tasks was a real problem and a third of uncoloured events was mostly cosmetic.

What is missing. These three stores still learn separately. The vocabulary knew the course's name for months while the tagger had no idea it meant coursework — that link was only added recently, and nothing yet connects task tags to event categories, so "Running" and "Gym" exist as event labels with no home in the registry and no relationship to "Exercise". A two-level hierarchy is the intended fix and is not built.

Where it gets interestingthe cases that only exist because the parts meet

09What it actually knows about time

Sundown is computed from your latitude and longitude with astral, and the Hebrew date from pyluach — both pure Python, no lookup. That makes Shabbat a moving boundary rather than a day of the week. 

Fri  4 Sep   candles 18:43   →  19:00 falls inside Shabbat
Fri 18 Dec   candles 16:20   →  17:00 falls inside, 16:00 does not
Sat  5 Sep   tzeit   19:37   →  20:00 is out

A repeating event skips those windows, with three exceptions that are all about intent: meals are allowed because they are what the day is for (unless it is a fast — Yom Kippur is both, and the fast wins); a series anchored on Shabbat keeps it, because a Saturday shiur was put there deliberately; and if observance cannot be computed, nothing is skipped, because a series quietly losing days is worse than one landing where it should not.

09bThe model proposes, arithmetic disposes

The most useful pattern in the system shows up where language models are weakest: planning six weeks of training around a calendar of festivals whose boundaries move with the sun.

A model is genuinely good at the shape of such a plan — how hard, how often, in what order, what a sensible week looks like. It is reliably bad at the dates, because nothing in its training tells it which Tuesday is a fast day. A model that has confidently scheduled a hard session on one is not a hypothetical; it is the default behaviour of any model that has not been told.

So the two are separated by force. The model's output is a proposal, and every date in it is re-placed by deterministic code against computed availability before anything is written. What lands on the calendar is the model's judgement about training and the arithmetic's judgement about days.

The same line, drawn twice

One more split sits inside the deterministic half, and it is what keeps that half honest: what is computed and what is merely preferred live in different modules. Whether a day is available is not negotiable and is calculated. Whether two hard sessions may fall on consecutive days is a preference someone can reasonably disagree with. Mixing them would let a preference quietly override a boundary — so they are not editable in the same file.

Generalised, this is the shape the whole system uses. The routing threshold in section 03 is the same idea at the scale of one sentence: let the model do the part that needs judgement, and never let it do the part that has a right answer.

10More than one thing at once

A single sentence can hold two events, and the rule parser cannot: it has one set of slots. Rather than fill half of them it refuses outright — RuleParserSkip — and the sentence goes to llama whole. A softer version of the same instinct is in the score: two clock times in one span multiplies confidence by 0.70, because "lunch at noon and coffee at 9" is usually two things wearing one sentence.

Batching works the other way. Several commands can be sent as one request with each in brackets — [gym tomorrow at 7am] [lunch with Dana at noon] — and the server splits them and parses each alone. That is cheaper rather than dearer, because a short single command often settles on the rules for no model call at all, and the review runs once for the batch instead of once each.

Two commands sent asLLM calls
two separate requests4
[one] [two] — split and parsed apart3
"one and two" — one run-on sentence2

Joining is cheapest and worst: it buys one call by handing the model the run-on sentence it is least reliable on. Brackets are the middle, and the saving is the review, not the parse.

11Waiting, and coming back to it

Two different queues, easy to confuse because both are "later".

QueueWhat it holdsDrains when
the session queue pressing the mic while it is still thinking — the next thing you want to say, or (press again) more of the same sentence the current command finishes
the pending queue a command the model could not be reached for — Ollama down, laptop asleep. Stored with its transcript, never silently dropped a retry loop notices the model is back

Neither blocks you. The phone shows a queued command as pending and gets a notification when it finally ran, which is the only reason a command given on a train is still there when the laptop wakes up.

12Tasks are not small events

Eight of the fifteen actions are about tasks, and they behave differently from events in ways worth knowing: a task has no time, it has a list, and it can be finished.

PropertyBehaviour
list"today" or "general" — where it lives, and what a daily read covers
tagsinferred from the title, or from your own vocabulary
due dateoptional, and the only date a task has
subtasksa task can hold its own list; each completes separately
completionfinished, not deleted — the record survives

The distinction the parser has to make first is event or task, and it hinges on whether a time was spoken. "Remind me to buy milk" is a task; "buy milk at 6" is an event. That single judgement is why the self-check's routing rules spend most of their words on it.

13Reading the day back

Asking is a first-class action, not a search box. query_schedule and query_todos answer in sentences, and because they create nothing they are the one place the self-check may not act — there is no record to correct. 

"what do I have on friday"
  → You have one event Friday, 4 September: Dentist Appointment at 9:00 AM.

"what do I have this week"
  → You have 6 events this week: Team Standup at 9:30 AM, ...

A named day beats the relative scope: scope can only say today, tomorrow or this week, so "friday" used to fall through to today and answer confidently about the wrong day. It now carries an explicit date, and the answer names the day back to you — "Friday, 4 September" — so a misunderstanding is visible in the reply rather than discovered later.

The morning briefing is the same query with no question: it reads today's events aloud in order, in one sentence, and says "your schedule is clear" rather than nothing at all when there is nothing.

Down to the metalthe shapes, the wire format, the process model

14One request, end to end

Everything above happens inside a single HTTP request. Both clients — the desktop app and the phone — are thin: they capture audio, transcribe it, and post the text. Neither contains a parser. This is the whole contract: 

POST /voice/text
{
  "transcript":   "book gym tomorrow at 7am",
  "source":       "mac" | "ios" | "test",   ← the ONLY difference between clients
  "current_view": "month",                  ← disambiguates "delete that"
  "trace_run":    "run-8f3a"                ← optional; joins a live trace stream
}

200 OK
{
  "message":     "Added Gym tomorrow at 7:00 AM.",   ← spoken aloud
  "actions":     [{"action": "create_event", "parameters": {...}}],
  "refresh":     "switch_month",             ← view the client should show
  "parse":       "rule" | "hybrid" | "llm" | "error",
  "corrections": [...],                      ← vocabulary rewrites applied
  "trace":       [ ...stages... ],
  "memory_id":   417                         ← the row a 👍/👎 later attaches to
}

source carries more weight than it looks. It labels the trace, the vocabulary corrections and the command memory — and it defaults to "test", not to a real client. That default is deliberate and was once the other way round, which made an afternoon of scripted testing indistinguishable from real use in the history the model learns from. Forgetting to label a script is now harmless; forgetting to label a real client is obvious.

15The shapes the pieces pass each other

Three types carry everything. Knowing them is most of knowing the codebase.

What the rules hand over

@dataclass
class RuleParseResult:
    confidence:     float            ← the number section 03 is about
    intents:        list[tuple[str, BaseIntent]]
    missing_slots:  list[str]        ← non-empty ⇒ never fast-pathed
    raw_slots:      dict             {action: {slot: value}}
    transcript:     str
    routed_to_llm:  bool
    dropped_spans:  int              ← parts it could not route at all

Two fields decide routing, not one. A result is answered directly only when confidence >= 0.85 and missing_slots is empty — a high score with a hole in it still goes to the model. dropped_spans is the quieter signal: it counts parts of the sentence the rules never accounted for, which is how a half-understood command is told apart from a fully-understood one.

What validation is

Every action declares a Pydantic model, and that model is where the domain rules live — not in the parser, and not in the executor. A spoken time reaching CalendarIntent as "230PM" is normalised to "14:30" by a field validator; one reaching it as "99:99" is rejected outright, and the rejection is what triggers a re-parse. The parser cannot produce an invalid record because the type will not hold one.

How an action is defined

Adding a capability means adding a directory, not editing the pipeline. Every action declares four things, and the third and fourth are the interesting ones: 

class CreateTodoAction(BaseAction):
    action_name:       "create_todo"
    description:       prose the model reads to decide when to use it
    intent_model:      CreateTodoIntent
    parameters_schema: a JSON Schema fragment

    def execute(self, intent, config) -> str:   returns what gets spoken

description and parameters_schema are not documentation. They are concatenated into the system prompt and into the JSON schema the model is constrained to emit — so the registry generates the prompt. An action's prose about when to use it is, literally, how the model learns to use it. That is also why prompt-engineering in this system means editing a class attribute next to the code it describes.

16What the model is actually sent

Not a question in English. Four pieces are assembled, and the last one is what makes the output parseable rather than hopeful:

PieceBuilt fromRoughly
action catalogueevery registered action's description + schema~4k tokens
today's date tablerebuilt when the date changes, cached in betweensmall
your past commandsthe four most similar, from memory~710 chars
the transcriptafter vocabulary correctionone line

The catalogue dominates, and it is identical between calls — which is the point. The date table is rebuilt only when the day changes, so the long prefix stays byte-identical and the model's prefix cache keeps hitting. When that cache is missed the same call takes 30–60 seconds instead of 8; an early version had the context window set below the prompt's own length, so every single call overflowed and re-processed the whole thing.

The output is constrained, not requested

POST localhost:11434/api/chat
{
  "model":  "llama3.1:8b",
  "format":  { ...JSON Schema assembled from the registry... },  ← the model CANNOT emit prose
  "stream":  false,
  "keep_alive": -1,                       ← never unload between commands
  "options": { "temperature": 0.1, "num_ctx": 8192 }
}

format is a grammar constraint at sampling time, not an instruction — the model is unable to produce a token that would break the schema. So the failure mode is a valid object with wrong values, never a parse error, which is exactly why the layer after this one exists. The self-check runs the same way but at temperature 0.0: a judgement that varies between runs is not a judgement.

17When the thing you named does not exist

A parse can be perfectly well-formed and still refer to nothing. "Mark the dentist appointment done" is a valid complete_todo — but if there is no such task, executing it is not an error, it is a miss. The two need different handling, and conflating them is how a confidently-wrong rule parse used to reach the user as "I couldn't find…". 

class AssistantError(Exception):        something broke
    ├── STTError, OllamaError, ParseError, ...

class TargetNotFound(Exception):        nothing broke — the target isn't there
    deliberately NOT an AssistantError

That inheritance gap is load-bearing. TargetNotFound is caught separately and triggers escalation: the sentence goes back to the model with the failed interpretation attached, and is re-read from scratch. It is the safety net under the confidence score — the case where the rules were sure, and wrong, and the only evidence is that reality disagreed.

Escalation is not retry. The command is re-parsed, not re-run. If the second reading also matches nothing, the answer is "I couldn't find it" and the slot stays empty. For a delete, an empty slot is the correct outcome: guessing which record was meant is worse than admitting the miss.

Choosing a file over a socket buys three things at once: the panel floats over a full-screen app with the calendar closed, a command spoken to the phone is visible on the desktop without either knowing about the other, and the log is the durable record the history view reads back. A crashed reader loses nothing; a restarted one catches up.

The failure this shape causes

Only the API reloads itself when its code changes. The desktop app and the thinking panel do not, and the phone needs a reinstall — so a change can be live in the brain and stale in three places at once. "It had no effect" is, more often than not, this.

One more constraint the process model imposes: two model loads on separate threads segfault the interpreter. The test suite pins the numerical library to one thread to avoid it, and the API refuses to warm its models up when running under test — a test that builds the app wants its routes, not its weights.

19Sundown, computed rather than looked up

Section 09 said the system knows when Shabbat begins. This is how, because it is two independent questions answered by two different means — and conflating them is the classic way to get it wrong.

QuestionAnswered byNature of the answer
Which days are holy?the fixed rabbinic calendar, computedexact — it is arithmetic
At what time?solar position from your coordinatesastronomical, ±1–2 min
 
# which days — computed from the calendar's own arithmetic, not a lookup table
HebrewDate.from_pydate(date).festival(israel=True, include_working_days=False)
    → a name only when work is forbidden; None on intermediate festival days

# what time — solar geometry at the configured latitude and longitude
sunset            = astral.sun(observer, date)["sunset"]
candle_lighting   = sunset − 18 min          configurable
tzeit (it ends)   = dusk at 8.5° below the horizon   configurable

include_working_days=False is doing real work: the alternative call returns a name on the intermediate days of a long festival too, which would blank out an entire free week as though it were a holiday. The distinction between a day when work is forbidden and a day merely inside a festival is the one the whole module is built on.

Why a date is not enough

Friday          sunset   candles   ends (Sat)   gap
2 Jan           16:47     16:29      17:28      40 min
26 Jun          19:51     19:32      20:33      43 min
18 Dec          16:38     16:20      17:18      40 min

Over three hours of drift across the year. A 19:00 event on a Friday is comfortably outside the boundary in June and well inside it in December — so a rule written against dates alone is wrong for a whole season, silently, in the direction that books things where they should not be.

Two slots per day, not one

A day here runs sundown to sundown, so every civil date is modelled as two independently governed halves: the daytime is governed by that date's own status, and the evening by the following date's. This is why a Saturday night can be free in one week and blocked in the next — if another festival day begins at sundown, the evening was never Saturday's to give.

How we know the arithmetic is right

Computing a time rather than fetching one has an obvious hazard: it is unfalsifiable on its own. A wrong sundown looks exactly like a right one until something independent disagrees, and by then a season of Friday evenings has been filed on the wrong side of the boundary.

So the published times were fetched once, from a reference that states nightfall using the same definition — the same degrees of solar depression — and checked in as a fixture. The comparison then runs offline, for ever: 

126 comparisons · 6 cities · 7 dates across a year · 3 times each
worst disagreement: 28 seconds

Every one of these times is displayed and acted on to the minute, so agreement inside half a minute means the computed answer and the published one are the same answer. The cities are chosen to break things rather than to pass: a southern latitude catches a hemisphere assumption, a negative longitude catches a dropped sign, and two of the dates sit either side of a daylight-saving changeover. A fixture of convenient dates near home would prove nothing.

The model is not consulted here, ever. It may propose a date; whether that date is available is decided by this code, deterministically. And if the computation cannot be done at all — an unreachable configuration, an out-of-range date — nothing is skipped. A series that quietly loses days is worse than one that lands somewhere it should not, because the second is visible and the first is not.

20A repeating event is not a rule, it is rows

"Every day at 7pm until October" could be stored as a pattern and expanded when something asks. It is not. The occurrences are written as ordinary individual rows, each with a series_id pointing at the first, and every query in the system stays a plain date lookup that knows nothing about recurrence.

ConsequenceWhy it follows
one occurrence can be edited aloneit is a row; nothing else references it
a skipped day simply is not writtenno exception list to keep in step with the rule
an unbounded series stops after a yearrows are finite, so a horizon is required
"delete from here on" re-roots the seriesdeleting the root would orphan the past occurrences

The third row is the honest cost: a series with no stated end is written a year forward and no further. The fourth is the subtle one — if you delete from a date that includes the first occurrence, the series is re-rooted onto the earliest instance still standing, so the ones before it stay linked to something that exists.

This is also what makes the Shabbat rule in section 09 cheap. Skipping is a decision taken once, at write time, per candidate date — not a filter every reader has to remember to apply. A row that should not exist is never created, so no query anywhere can accidentally return it.

21Two devices, one truth, no merge

The phone holds a full local copy and works with the laptop switched off, which raises the question every offline-capable app has to answer: what happens when both sides changed the same thing? The answer here is deliberately not "merge".

Edits carry the version they were made against

PATCH /events/42
{ "start_time": "16:00",
  "base_updated_at": "2026-09-02T14:11:03Z" }   ← the copy I edited

409 Conflict — "changed on the Mac since you edited it"

The device quotes the version stamp it worked from. If the record has moved on since, the write is refused rather than applied, and the phone says so. Losing an edit loudly beats losing one silently, and for a calendar with a single human writing to it, that is the whole of the concurrency story.

Polling that costs almost nothing

Refetching every list on a timer is expensive, so the phone used to do it every 30 seconds — meaning something added on the laptop could sit invisible for half a minute. This returns a few bytes derived from the database file itself, so the phone can ask every couple of seconds and do real work only when the answer changes. It relies on one property of the storage engine: in rollback-journal mode every commit touches the main file, so modification time and size together move on any write.

What a queued command is worth

A command spoken with the laptop unreachable is queued on the phone and replayed on reconnect — but it is queued as text, not as an action. It is parsed when it finally arrives, against the calendar as it is then. That is the right way round: an instruction is a thing you meant, not a diff you computed, and re-deciding it later with better information is strictly better than replaying a stale conclusion.

22The one door to the outside, and its three locks

Everything so far runs on one machine. There is one deliberate exception, off by default and configured by hand: a two-way sync with a hosted calendar. It is worth describing precisely, because "syncs with your work calendar" is exactly the kind of feature that quietly turns a local system into a networked one.

LockWhat it prevents
only events that came from the remote are ever pusheda private local event silently appearing in a work calendar
remote-origin events are read-only unless two-way is onedits marked for a push that will never happen, diverging for ever
subscribed feeds are always read-onlywriting to something with no write path at all

The first lock is the important one and it is structural rather than a setting: push-eligibility requires the row to already carry a remote id. A locally created event has none, so there is no code path by which it can leave — not "we remember not to", but "there is nothing to send it as".

Conflicts, and deletes that survive a failure

Conflict policy is last-write-wins, decided during the pull by comparing timestamps: if the local edit is newer, the remote version is not applied and the row is kept marked dirty for the next push. Deletes cannot work that way — a deleted row cannot carry a flag — so deletion writes a tombstone to a queue, which the sync drains and re-queues on failure. Without it, deleting while offline would delete locally and leave the remote copy for ever.

So the honest version of "nothing leaves the machine" is this: the part that decides things — transcription, parsing, the model, the calendar arithmetic, sundown — has no network path at all, and a test fails the build if that changes. Storage and decision-making are local absolutely. Distribution is local by default: the phone reaches the laptop directly, and the only way anything reaches a third party is if you configure this feature and connect an account. It is off, and the code contains no credentials for it.
